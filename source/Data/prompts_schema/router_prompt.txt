# Yuzu Query Router — Design Notes

## Purpose

One router call per turn, producing:

- Retrieval intents: `websearch`, `doc_retrieval`, `rag_retrieval` — arrays of standalone queries, empty if not needed
- Memory candidates: `user_preferences`, `user_decisions`, `user_events`, `user_tasks` — reconciled against existing state, not blindly appended

Schema file: `router_schema.json` (pass as the `format` field in the Ollama API call — see below).

## Why reconciliation, not raw extraction

An LLM classifying free text has no way to know "this is the same preference as before" unless it's shown the existing state. So the router call needs two things in context:

1. **Current state** — the existing preferences/decisions/tasks, compact (id + short statement, not full history)
2. **The new turn**

The model's job is then to reconcile, not just extract: for each candidate fact it emits `add`, `update` (with a `replaces` id pointing at the superseded item), or `no_change`. It should only actually emit items that are `add` or `update` — `no_change` items don't need to be re-output at all; the field exists mainly to give the model an explicit "nothing changed" option instead of forcing an add.

Your application code — not the model — applies the diff:
- `add` → append to the store with the new id
- `update` → replace the item at `replaces` with the new statement, keep the id or roll to a new one, your call
- Never let the model re-output the whole merged list; that's wasteful and error-prone once the list gets long. Diffs only.

## Field definitions

**websearch / doc_retrieval / rag_retrieval**
Query generation, not classification. Rewrite the user's need as a standalone query — resolve pronouns, pull in context missing from the raw message. `doc_retrieval` only fires when documents are attached *and* the message needs their contents. Most turns should produce empty arrays for all three.

**user_preferences**
Only the user's own preferences, or a closely related person's preference the user explicitly ties to their own decisions (a recurring collaborator's constraints). Third-party opinions mentioned in passing — "my professor likes Rust" — are not preferences. Enforce this explicitly in the prompt; models default to over-extracting here.

**user_decisions**
Forward-looking commitments — "using Postgres instead of Mongo from now on." If a new decision contradicts an existing one, that's an `update` with `replaces` set.

**user_events**
Things that already happened — outcomes, good or bad. Not forward-looking. Tag `sentiment`.

**user_tasks**
Unfinished or deferred work. Track `status` (`open` / `in_progress` / `done` / `deferred`) alongside the usual `add`/`update`/`no_change` action.

### Disambiguation

These three overlap heavily in casual text ("I decided to finally fix the bug and it worked" is an event *and* a decision). Don't force mutual exclusivity — let one sentence populate more than one field. Give the model a decision tree instead of parallel definitions:

- Did something **happen** (already occurred)? → event
- Is the user **committing to an approach going forward**? → decision
- Is there **unfinished work** implied? → task

## Ollama usage

Ollama's structured-output support takes a JSON Schema directly in the `format` field of `/api/chat` or `/api/generate`. Load `router_schema.json` and pass it as-is:

```python
import json, requests

with open("router_schema.json") as f:
    schema = json.load(f)

existing_state = {
    "user_preferences": [...],  # compact: id + statement only
    "user_decisions": [...],
    "user_tasks": [...],
}

system_prompt = f"""You are Yuzu's turn router. Given the user's message and their
current known preferences/decisions/tasks below, output retrieval queries and any
NEW or CHANGED memory items.

Current state:
{json.dumps(existing_state)}

Rules:
- Only extract a preference belonging to the user themselves, or a closely
  related person the user explicitly ties to their own decisions. Ignore
  third-party opinions mentioned only in passing.
- If a new statement contradicts or supersedes an existing item, use
  action "update" and set "replaces" to that item's id.
- If it's genuinely new, use action "add".
- Do not re-emit items that haven't changed.
- websearch/doc_retrieval/rag_retrieval queries should be standalone
  (resolve pronouns and missing context from the raw message).
"""

resp = requests.post("http://localhost:11434/api/chat", json={
    "model": "gemma3",
    "messages": [
        {"role": "system", "content": system_prompt},
        {"role": "user", "content": user_message},
    ],
    "format": schema,
    "stream": False,
})

router_output = json.loads(resp.json()["message"]["content"])
```

## Open question worth testing

This one call is doing a lot: retrieval routing + memory reconciliation + event/decision/task extraction. Worth benchmarking whether splitting into two calls (a retrieval-router and a memory-extractor) gets better precision from a small local model than asking for everything in one pass — especially relevant given Yuzu's embeddings already run on a small local Gemma3 model, so the router is likely similarly sized.
